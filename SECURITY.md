# Security

## Reporting a problem

Please report security issues privately, through GitHub's **Report a vulnerability** button on the repository's Security tab, rather than in a public issue. Include the `.es` file (or the steps), the command you ran, and what happened. You'll get an answer as soon as possible, and a fix will be credited to you unless you'd rather it wasn't.

## What the compiler guarantees

- **No shell.** The compiler never runs a command line through a shell (`system`, `popen`, `sh -c`). It starts the C compiler (`cc`) and, for `run`, the program itself with `fork` and `execvp`, passing each argument separately, so file names and program text are never interpreted as shell syntax.
- **Escaped output.** Everything from the source program that ends up in the generated C is escaped or rebuilt: text values and the source lines kept for runtime errors are written as C string literals with every quote, backslash, `?` and non-printing byte escaped (octal escapes for bytes outside printable ASCII), and names become C identifiers made only of letters, digits and `_`. Comments in the generated C hold only line numbers. A program can't inject C code.
- **Private temporary files.** Each command makes its own directory with `mkdtemp` (under `$TMPDIR`, or `/tmp`), readable only by you, holds the generated C and the program there, and removes it when it finishes, including after errors.
- **No environment hooks in built programs.** The runtime has test hooks that read environment variables (`ES_SKIP_OUTPUT`, `ES_ANSWERS`, `ES_DEBUG_MEMORY`, `ES_MEMORY_LIMIT`, and `ES_NOW` and `ES_RANDOM_SEED`, which fix the clock and the random numbers). They're compiled in only when the compiler is asked for them (`ES_HOOKS=1` with `easyscript run`, which only the test suite and the interactive shell set). A program made with `easyscript build` never reads them, so nobody running it can make it skip output, read answers from a file, or append to one. `make test` checks this (`cli/no-env-hooks-in-built-programs`).
- **Runtime errors, not crashes.** Generated programs check list and text positions, division by zero, map keys, records that can be nothing, recursion depth, and every allocation, and stop with a plain-English error instead of reading or writing memory they don't own. The test suite runs every program under AddressSanitizer and UndefinedBehaviorSanitizer (`make test-debug`).

- **File and folder sentences only touch the paths the program names.** No library sentence runs a shell or a command. Making, renaming, copying and moving never replace something that's already there. Deleting needs the program to name the file or folder (`delete the file "old.txt"`); a folder is only deleted if it's empty, unless the sentence says `and everything in it`, which refuses `"/"`, `"."`, `".."`, `"~"` and `""` (paths that mean more than one folder of yours) and removes links inside the folder without following them.
- **Programs run other programs only from a list of words, never through a shell.** `run "git" with "log" and name` starts `git` with `fork` and `execvp`, giving it `log` and the value of `name` as separate words, exactly as they are: spaces, quotes, `;`, `|`, `&`, `$`, backticks, `*` and `~` in them are ordinary characters, so text that came from a user, a file or the words given to the program can't start a second command or expand into other words. The program's name is looked up in `PATH` like a terminal does, unless it contains a `/`. There's no phrase that runs a command line; a program that wants a shell has to name it (`run "sh" with "-c" and ...`), and then the usual care with shell text is the programmer's.
- **The terminal is always put back.** The keyboard's key-at-a-time mode is turned off when the program ends, after a runtime error, on Ctrl+C (and SIGTERM, SIGHUP and SIGQUIT), and before `ask` or running another program; signals the program was started with ignored stay ignored. `make test` checks this on a pseudo-terminal (`keys/terminal-restored`).
- **Programs of several files only read the files they name.** `use helpers.` reads `helpers.es` from the folder of the file that says it, and nothing else.

## What it doesn't do

- EasyScript programs can read, write, rename, move and delete any file the user running them can (`write ... to file`, `read file ...`, `delete the folder ... and everything in it`). Don't run a program you don't trust.
- `delete the folder D and everything in it` follows the path the program gives: a program can still delete a big folder by naming it (`"/Users/me"`). The check above only stops paths that are wider than any one folder by mistake.
- The compiler trusts the C compiler it finds as `cc` on your `PATH`, and `run "git"` runs whatever `git` is first on the `PATH` of whoever runs the program. A program that must run one particular program can name it by its path (`run "/usr/bin/git"`).
- `the words given to the program`, `the text sent to the program` and `the setting called X` are whatever whoever started the program chose; a program that uses them to name files to delete or programs to run should check them first.
